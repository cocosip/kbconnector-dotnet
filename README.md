# KingbaseConnector

Independent managed ADO.NET driver for KingbaseES, developed against the [design and feature matrix](docs/README.md). V9 is the first target; V8 and EF Core providers follow later.

This is an early development build. Package identity and licensing are provisional. Bounded live bootstrap and PG execution results are recorded in the [progress tracker](docs/kbconnector-development-progress.md); complete server compatibility and release readiness remain pending. The tracker reports delivered subfeatures, mode/backend coverage and acceptance separately; its parent-requirement closure inventory is not an implementation percentage.

The core targets `netstandard2.0`, `netstandard2.1`, `net8.0`, `net9.0`, and `net10.0`. Install an SDK that supports `net10.0` and `.slnx`, plus the .NET 8/9/10 runtimes, then run:

```powershell
./eng/verify.ps1
```

This restores, builds, runs offline tests, packs, and runs a consumer for each explicitly selected package asset. Standard assets run on .NET 8; this does not certify .NET Framework or other platforms. Tests do not contact a database by default. The separate [private live suite](docs/live-testing.md) reads external process configuration; missing configuration fails when LIVE is explicitly enabled.

The [CI/CD workflow](docs/ci-cd.md) runs these checks on Windows and Linux for master pushes, pull requests and manual runs. A pushed version tag matching `Directory.Build.props` enables NuGet trusted publishing for core/DI and generates a GitHub Release after both OS jobs pass. `./eng/verify.ps1 -ContinuousIntegration` also produces TRX reports locally. Hosted workflow execution and publishing-policy setup remain separate acceptance evidence.

Official reference DLLs are comparison inputs only and are excluded from product references and packages.

PG-wire connections expose command/Wait-driven notifications in the four tested compatibility modes:

```csharp
listener.Notification += (_, message) => HandleMessage(message.Channel, message.Payload);
using var listen = new KingbaseCommand("LISTEN \"app_events\"", listener);
await listen.ExecuteNonQueryAsync(cancellationToken);
bool received = await listener.WaitAsync(TimeSpan.FromSeconds(5), cancellationToken);
```

`KingbaseNotificationEventArgs` exposes the sender `ProcessId`, `Channel` and `Payload`; channel/payload are server-supplied application data and are not automatically logged. There is no continuous background dispatch outside an explicit operation. Commands, waits and active COPY exchanges deliver notifications while owning the connection; handlers must return promptly and cannot reenter commands, schema calls, Wait or that COPY resource. Other connections can perform independent work. Handler failures are surfaced after command acknowledgment and result/metadata validation, before a Reader is published; server errors and confirmed rollback outcomes take precedence. Already acknowledged writes are not undone. A handler failure during BEGIN triggers bounded rollback cleanup; failed cleanup closes the connection.

`Wait(int timeoutMilliseconds = -1)` and `WaitAsync(int timeoutMilliseconds = -1, CancellationToken = default)` return true for a received notification and false on timeout. TimeSpan overloads require exact milliseconds; -1ms is infinite and zero polls. Wait requires an idle connection outside a transaction and sends no SQL. Timeout and caller cancellation preserve the session, including an incomplete notification frame, for the next Wait or command. At most one bounded frame read may finish after a wait ends; it is retained without dispatch until another explicit operation consumes it. Late frames are not consumed by an expired wait. Ordinary command cancellation retains its existing physical-retirement policy. Close aborts a wait and revokes ownership; malformed messages, EOF or fatal idle errors retire the session. Wait's deadline bounds I/O waiting, not application handler execution.

LISTEN/NOTIFY follows server transaction semantics: rollback does not publish notifications and commit makes them available. Closing a pooled borrower clears the callback sink before cleanup, discards queued notifications and removes LISTEN subscriptions. A later borrower or a reconnected client must issue LISTEN again. Notifications are not durable and the driver does not replay missed messages or automatically resubscribe. Native MySQL wire notification support, broader profiles/platforms and real-server TLS remain outside the current acceptance evidence.

Subscribe to `KingbaseConnection.Notice` for structured server diagnostics during commands or explicit waits. `KingbaseNoticeEventArgs.Notice` exposes `SqlState`, localized `Severity`, optional `InvariantSeverity`, `MessageText`, `Detail`, `Hint` and an immutable `Fields` dictionary keyed by protocol character. Raw fields may contain sensitive application data; the driver does not log them, and `KingbaseNotice.ToString()` includes only SQLSTATE. Startup, unowned and pool-reset notices are parsed and discarded.

Notice handlers share notification ownership and reentry restrictions. The first handler exception from either event is surfaced after command synchronization and result validation, with server/protocol/schema errors and confirmed rollback taking precedence. During idle Wait, a notice alone does not return true; a Notice handler exception stops that wait immediately after its complete frame and preserves a healthy connection. Default severity handling follows the server's message settings. Complete error-tail/profile/platform acceptance remains tracked separately; the tested SQL Server profile's Error/CommandComplete/Ready tail still causes strict physical retirement.

Client COPY streams support the four tested PG-wire compatibility modes:

```csharp
using (var writer = await connection.BeginTextImportAsync(
    "COPY app_items (id, description) FROM STDIN", cancellationToken))
{
    await writer.WriteAsync("1\tfirst item\n2\t\\N\n");
    ulong rows = await writer.CompleteAsync(cancellationToken);
}

using var export = await connection.BeginRawBinaryCopyAsync(
    "COPY app_items TO STDOUT (FORMAT BINARY)", cancellationToken);
await export.CopyToAsync(destination, 81920, cancellationToken);
ulong? exportedRows = export.RowsCopied;
```

`BeginTextImport`/`BeginTextImportAsync` returns a `KingbaseTextCopyWriter`. Complete flushes strict UTF8 without a BOM and waits for the server's COPY count and ReadyForQuery. Dispose also completes text import. To abandon an import, call Cancel/CancelAsync before disposing; buffered text is discarded and CopyFail is acknowledged. The SQL COPY options define CSV, delimiters, quoting, escapes and NULL; the driver sends the text without translating it. `BeginTextExport`/`BeginTextExportAsync` returns a strict UTF8 TextReader that preserves BOM characters as data.

`BeginRawBinaryCopy`/`BeginRawBinaryCopyAsync` returns a `KingbaseCopyStream` with server-confirmed `IsImport`, `IsBinary` and `ColumnCount`. It preserves opaque binary bytes, including the tested server's KBCOPY signature. Raw import requires explicit Complete/CompleteAsync; disposing an unfinished raw import cancels. Export completes only after all CopyData, server CopyDone, COPY count and ReadyForQuery; `RowsCopied` remains unknown until success is acknowledged. Counts already acknowledged remain available if a callback later fails. Disposing an unfinished raw or text export closes the physical session. Raw binary data requires matching source/destination formats and types; this API does not promise backup, cross-version restore or typed binary row codecs.

Only a single client COPY statement with FROM STDIN or TO STDOUT is accepted. Server files/PROGRAM and known text-direction mismatches reject before sending SQL. COPY owns the connection until terminal synchronization, so commands, schema calls, transactions and waits reject while it is active. Import continuously consumes server messages under that ownership to avoid read/write backpressure deadlocks; synchronous event handlers may run while writes are pending. Handler exceptions are retained until terminal synchronization, with actual server/protocol errors taking precedence. There is no receive task after COPY ends.

Command Timeout is one lifetime deadline, including application pauses; zero is unlimited. The token supplied to Begin remains applicable for that resource's lifetime. An in-flight I/O cancellation or connection Close retires the physical session; pre-canceled calls do no I/O. Explicit import cancellation uses the separate Cleanup Timeout and consumes only its own acknowledged 57014; known earlier server/receive failures remain visible. It does not roll back an enclosing transaction: the tested profiles report a failed outer transaction, which the application must explicitly roll back. Concurrent operations on the same COPY resource reject, including cancellation during unacknowledged completion; use an I/O token or connection Close to interrupt pending work.

COPY data streams beyond the buffered query's 1 MiB total limit. Frames remain bounded to 64 MiB and total control/empty-message traffic to 4096 frames/1 MiB. Shared byte-array I/O and the declared modern Span/Memory overrides split data into chunks of at most 64 KiB; Span/Memory adaptation may stage one additional chunk. The netstandard2.0 asset exposes the shared byte-array contract; later host BCL adapters are outside that memory guarantee. TextReader.ReadToEnd and application destination buffers can deliberately materialize the result. Typed binary COPY, ordinary BLOB/CLOB binding, broader platforms/profiles, native MySQL wire and real-server TLS remain separate acceptance work.

OID large objects use an explicit local transaction on the four tested PG-wire modes:

```csharp
using var transaction = await connection.BeginTransactionAsync(cancellationToken);
var objects = new KingbaseLargeObjectManager(connection);
uint oid = await objects.CreateAsync(cancellationToken: cancellationToken);
using (var stream = await objects.OpenReadWriteAsync(oid, cancellationToken))
{
    await input.CopyToAsync(stream, 65536, cancellationToken);
    stream.Position = 0;
    await stream.CopyToAsync(output, 65536, cancellationToken);
}
await objects.UnlinkAsync(oid, cancellationToken);
await transaction.CommitAsync(cancellationToken);
```

`Open` accepts FileAccess.Read, Write or ReadWrite. Streams support byte-array Read/Write, Position, Length, 64-bit Seek/SeekAsync and SetLength/SetLengthAsync. Length restores the previous cursor before returning. There is no client write buffer; Flush validates ownership. Create accepts an optional UInt32 OID, with zero asking the server to allocate it. OID values, bytea and ordinary BLOB/CLOB/NCLOB binding are separate contracts.

Every operation requires a healthy explicit transaction and exclusively owns the connection until it completes; ordinary commands may run between stream operations. Commit, rollback, Close and pool return invalidate old handles. Public savepoint rollback invalidates descriptors opened in its reverted scope while preserving older ones. Successful raw rollback conservatively invalidates all handles because raw savepoint scope cannot be trusted. Unlink invalidates handles for that OID. Disposing an invalidated handle cannot close a subsequently reused descriptor. Disposing in a failed transaction defers a surviving descriptor's close until a later large-object operation after recovery; ending the transaction releases remaining descriptors.

One Command Timeout covers all SQL in each operation. Close and deferred close additionally use Cleanup Timeout. Cancellation after I/O starts retires the physical session; pre-canceled calls and cancellation of operations that send no SQL preserve it. Acknowledged effects are never replayed or implicitly committed. Notice/notification callbacks finish after ownership and result checks; an unpublished Create/Open is cleaned up independently if callback delivery fails, or its session is retired. Byte-array transfers use chunks of at most 64 KiB without buffering an entire object. Inherited BCL Span/Memory adapters may allocate for the caller's full buffer; use byte-array methods or CopyToAsync with a bounded buffer when memory bounds matter. Broader platform/profile, privileges, exact-package LIVE and ordinary B05 LOB acceptance remain open.

Ordinary BLOB/CLOB/NCLOB parameters are supported on the tested Oracle and MySQL PG-wire profiles:

```csharp
using var command = new KingbaseCommand(
    "INSERT INTO app_documents (content, description) VALUES (:b, :c)", connection);
command.Parameters.Add(new KingbaseParameter("b", bytes) { KingbaseDbType = KingbaseDbType.Blob });
command.Parameters.Add(new KingbaseParameter("c", description) { KingbaseDbType = KingbaseDbType.Clob });
await command.ExecuteNonQueryAsync(cancellationToken);
```

`Blob` requires Byte[]; `Clob` and `NClob` require String. Typed DBNull is supported. Selectors resolve the verified Oracle `pg_catalog` or MySQL `sys` domain and its actual base OID, I/O identity and layout; unavailable modes reject before execution. An explicit qualified DataTypeName can select the same proven domain. Byte arrays retain input snapshot isolation. These are ordinary parameters and result values, separate from OID large-object descriptors.

Reader GetBytes/GetChars provide buffered partial reads and lengths; character lengths/offsets count UTF16 code units. Partial reads reuse private decoded bytes and validated strings for each current-row column, while public byte-array values remain independently mutable. GetStream/GetTextReader return buffered views, with no network SequentialAccess promise. The ordinary command exchange retains its 1MiB aggregate encoded limit; large binary escape output can reach that limit before the original bytes do. Stream/TextReader parameter inputs, unbounded LOB transfer, native MySQL wire and full B05 acceptance remain open.

Real prepared inputs preserve empty BLOB as non-NULL zero-length bytes in both tested modes. Oracle converts empty CLOB/NCLOB input to NULL; MySQL preserves empty text. The driver sends the supplied value without inventing that conversion. Ordinary PG and SQL Server profiles do not provide these named LOB types; their bytea/text and binary mappings remain separate contracts.

`KingbaseNumeric` preserves high-precision numeric values without rounding:

```csharp
var value = KingbaseNumeric.Parse("123456789012345678901234567890.00100");
Console.WriteLine(value); // Preserves the coefficient and scale, including trailing zeros.
```

`ToDecimal()` converts exactly or throws `OverflowException`, including when conversion would round a nonzero digit. The value representation currently bounds coefficient precision and nonnegative scale to 16,384 each; these are client resource limits. Bounded PG numeric LIVE evidence exists; complete server bounds, other modes and binary formats remain open.

The public input model includes `KingbaseParameter`, `KingbaseDbType` and `KingbaseParameterCollection`:

```csharp
var parameters = new KingbaseParameterCollection();
parameters.AddWithValue("amount", 1.2300m).Scale = 2; // Exact input constraint; never rounds.
parameters.Add("optional_id", KingbaseDbType.Integer).Value = DBNull.Value;
```

Each parameter belongs to one collection; nonempty names match case-insensitively with an optional `@`/`:` prefix. The PG-wire path resolves actual catalog types, requires an explicit type for NULL, snapshots mutable byte inputs, and rejects unsupported directions or lossy size/precision/scale constraints. Complete mode-specific parameter coverage remains pending.

The scalar catalog also supports optional `pg_catalog.int16` as `BigInteger` across all five assets, with the exact signed 128-bit range. Explicit `KingbaseDbType.Int128` selects it. Native mappings, when proven by the actual mode/catalog, include Oracle `pg_catalog.tinyint` and MySQL `sys.tinyint` as `sbyte`, SQL Server `sys.tinyint` as `byte`, MySQL `sys.uint4`/`sys.uint8` as `uint`/`ulong`, and SQL Server `sys.bit` as `bool`. MySQL multibit `sys.bit` remains unsupported. Signed/unsigned tiny selectors widen losslessly to `int2` when needed; MySQL byte input uses `uint4`. `UnsignedInteger` widens to `int8` and `UnsignedBigint` to discovered `int16` when native unsigned types are absent. Their default result CLR types follow the actual wire type (`long`/`BigInteger`); explicit `GetFieldValue<uint>`/`GetFieldValue<ulong>` checks range. `uint` inference continues to select PG OID; use `KingbaseDbType.UnsignedInteger` for an unsigned numeric value. `DbType.UInt32` likewise retains OID selection unless combined with a compatible explicit unsigned selector. `byte`, `sbyte`, `ulong` and `BigInteger` infer their corresponding logical types. Conflicting selectors and out-of-range values reject before application I/O, including typed NULL conflicts.

Native `sys.varcharbyte`/`sys.bpcharbyte` strings are available in non-PG modes; SQL Server additionally supports `sys.nchar`/`sys.nvarchar`. Select the exact qualified `DataTypeName` or `VarcharByte`, `CharByte`, `NChar`, `NVarchar` enum value. Returned Unicode and padding are preserved. Parameter `Size` continues to constrain UTF-16 characters for strings or bytes for binary input; it does not emulate server byte/national-character modifiers and never truncates. Optional native discovery requires proven layout and I/O identities. A synchronized ordinary permission/unsupported-catalog rejection leaves proven PG types usable; native aliases remain unavailable. Fatal, inconsistent or unsynchronized responses fail initialization. Pool reset refreshes native OIDs before reuse.

For PG XML, select `KingbaseDbType.Xml`, `DbType.Xml`, or `DataTypeName="pg_catalog.xml"` and supply a string or typed NULL. Ordinary strings continue to infer text. `DbType.String` can constrain the XML string representation; `DbType.Xml` requires XML. The actual XML catalog entry must have the supported base layout; missing XML rejects explicitly without making other types unavailable.

PG `bit`/`varbit` text values use `System.Collections.BitArray` in all four modes. Index 0 is the leftmost wire bit; leading zeros and exact bit count are retained, including non-byte-aligned values. `BitArray` infers `Varbit`; select `KingbaseDbType.Bit`/`Varbit` or the exact qualified `DataTypeName` for fixed/varying bit inputs and typed NULL. `DbType.Object` may constrain an explicit bit selector; a bare Object selector, Boolean/numeric/string/byte-array coercion, `Size` and numeric precision/scale are unsupported. Input snapshots copy mutable bits, including queued adapter rows; returned arrays are independent. The client text limit is 1,048,576 bits. Reader column size reports a positive declared bit modifier, never the current value's length. On the supplied Oracle profile, the server normalizes empty bit-string input to SQL NULL; other tested profiles preserve empty values. MySQL native `sys.bit` uses a different byte representation and remains unsupported; SQL Server `sys.bit` retains its separate Boolean mapping.

Native temporal selectors use the detected mode and actual `sys` catalog rather than treating same-named types as PG types:

| Selector | Mapping and input contract |
| --- | --- |
| `OracleDate` | `sys.date`: preserves date and time to whole seconds. `DateTime` default, `KingbaseTimestamp` provider (including BC/infinity). Fractional input rejects. |
| `SqlServerDate` | `sys.date`: finite years 1–9999, midnight `DateTime` or `KingbaseDate`; provider values retain that range. |
| `SqlServerDateTime` / `SqlServerSmallDateTime` | `sys.datetime` / `sys.smalldatetime`: `DateTime` with exact millisecond input; server calendar limits and minute rounding still apply. |
| `SqlServerDateTime2` / `SqlServerTime` | `sys.datetime2` / `sys.time`: `DateTime` / `TimeSpan` with all seven fractional digits retained. TIME must be below 24 hours. |
| `MySqlDate` | `sys.date`: `DateTime` default, lossless `KingbaseMySqlDate` provider. |
| `MySqlDateTime` / `MySqlTimestamp` | `sys.datetime` / `sys.timestamp`: `DateTime` default, lossless `KingbaseMySqlDateTime` provider, exact microseconds. |
| `MySqlTime` / `MySqlYear` | `sys.time`: signed `TimeSpan` through ±838:59:59 with exact microseconds; `sys.year`: `int`, allowing zero or 1901–2155 as client values while the server enforces its own constraints. |

These selectors also accept exact qualified `DataTypeName` and typed NULL. Calendar results require a confirmed ISO DateStyle snapshot. Native calendars require Unspecified `DateTime` Kind; the driver does not apply the machine timezone or a fixed offset. MySQL TIMESTAMP results preserve the server's displayed wall clock. Calendar-only native DATE also accepts `DateOnly` on modern assets; native TIME accepts `TimeOnly` there only when exactly representable by the selected type. Negative or long MySQL durations cannot be read as `TimeOnly`. Existing bare DbType selectors, DateTime and TimeSpan inference retain their PG mappings; new MySQL provider values infer their native DATE/DATETIME families. `Size` and numeric precision/scale remain unsupported for temporal parameters. Temporal modifier precision in declarations is server-owned; explicitly declare MySQL `(6)` or SQL Server `(7)` columns when needed.

`KingbaseMySqlDate` and `KingbaseMySqlDateTime` preserve zero/partial/invalid date components and years above the CLR range without substituting `MinValue`. Use `GetProviderSpecificValue` or `GetFieldValue<KingbaseMySqlDate>`/`GetFieldValue<KingbaseMySqlDateTime>` for such results; default DateTime conversion throws `OverflowException` if the calendar is not representable. The supplied MySQL profile rejects the tested zero/invalid dates and YEAR zero, while year 10000 has bounded LIVE provider evidence. Provider parsing and simulated results establish zero-value preservation; successful real-server zero-date acceptance remains open. Generic domains, SQL Server DATETIMEOFFSET, binary temporal formats, routine outputs/COPY and complete profile/platform acceptance remain separate work.

XML results use `String` through `GetString`, `GetChars` and buffered `GetTextReader`. The driver preserves returned text without parsing documents or resolving entities. Input/output use the confirmed UTF8 protocol encoding; an embedded XML declaration does not select another client encoding. Server validation, document/content settings and server serialization still apply. XML objects, `XmlReader`/`TextReader` input and binary XML are unsupported. Existing 1 MiB text/exchange limits apply; `GetTextReader` does not provide network streaming. The [live test guide](docs/live-testing.md) records the bounded PG acceptance.

`KingbaseConnection`, `KingbaseCommand` and `KingbaseFactory.Instance` expose bounded public PG-wire text execution in PostgreSQL, Oracle, MySQL and SQL Server compatibility modes. Default `Pooling=true` rents ordinary sessions in the detected compatibility mode through a direct or DataSource private pool; `Pooling=false` uses dedicated sessions. Open confirms product identity, actual mode and required catalog types; text commands bind values separately from SQL. Cancellation or an interrupted exchange closes the physical session; ordinary synchronized server errors allow reuse. `KingbaseException` exposes SQLSTATE safely; its explicit server text properties may contain sensitive data.

Application SQL retains its server dialect. The parameter planner recognizes Oracle q/nq strings, MySQL backticks and hash comments, and SQL Server bracket identifiers; it requires confirmed `standard_conforming_strings`. `@name` and `:name` are reserved provider markers, including in MySQL/SQL Server mode; quoted MySQL user-variable expressions are passed unchanged to the server, whose syntax/support still applies. `@@` system expressions remain server-owned. MySQL backslashes in SQL bodies delimited by single quotes, double quotes or backticks, and executable comments, reject before application I/O until SQL-mode interactions are confirmed; bind backslash-containing values as parameters. Dollar-quoted bodies preserve their literal contents without interpreting escapes. SQL blocks/multiple statements remain unsupported. Non-PG `GetSchema`, `KeyInfo`, generated commands and transaction chaining reject until their mode contracts are implemented. A cached PG-generated command retains this restriction after connection changes, including adapter batches. Native MySQL wire is a separate unimplemented backend.

Non-PG acceptance currently covers ordinary pooled session reuse/reset and supported catalog-OID scalar inputs/results, typed NULL/binary/numeric values, explicit preparation, buffered Readers/SchemaOnly, synchronized-error recovery and temporary-table sequential batches with explicit rollback. Native string mapping now enables ordinary SQL Server string literals; other unsupported result types still reject. Server semantics also differ: the supplied MySQL-mode profile returns NULL for integer division by zero, and SQL Server `count(*)` reports Int32. SQL Server savepoint rollback through `ROLLBACK TRANSACTION name` retains the active provider transaction. The tested profiles normalize non-ASCII UTF-8 bytes in application names to question marks; use ASCII application names when exact display matters. Unicode search paths retain their configured text. Pool reset binds the original mode to the physical session, rolls back unfinished transactions, discards session resources, reloads catalog OIDs, restores configured startup settings and checks the captured optional sql_mode value before reuse. Idle validation also rejects newly reported setting drift. Failed cleanup retires the session. Four-mode LIVE checks the same backend PID, dirty settings, temporary objects, preparations, failed transactions, LISTEN/advisory locks and Oracle/MySQL sql_mode restoration. This evidence does not establish full resource/load or type/routine/metadata parity.

On an open PG connection, `GetSchema()` and `GetSchemaAsync()` expose the five standard collections (`MetaDataCollections`, `Restrictions`, `DataSourceInformation`, `DataTypes`, `ReservedWords`), five object collections (`Schemas`, `Tables`, `Views`, `Columns`, `Sequences`), eight relational collections (`PrimaryKeys`, `UniqueKeys`, `ForeignKeys`, `ForeignKeyColumns`, `Indexes`, `IndexColumns`, `Constraints`, `ConstraintColumns`), two directories (`Databases`, `Users`), three routine collections (`Functions`, `Procedures`, `ProcedureParameters`) and four type collections (`UserDefinedTypes`, `TypeAttributes`, `EnumLabels`, `DomainConstraints`). Collection names are case-insensitive; null selects the 29-entry directory, including two aliases. The standard five have zero restrictions. `Restrictions` describes the collection filters and their one-based positions. Empty/unknown collection names or excess restriction values throw `ArgumentException`. Every call returns a fresh invariant-culture table and requires the connection to be free of active commands/Readers.

`DataTypes` lists the current session's cataloged, implemented scalar mappings, with actual unsigned `TypeOid` and `ProviderSpecificDataType` extension columns. Unsupported layouts and absent optional types are omitted. Unknown size, scale, operator and generation facts remain `DBNull`. `DataSourceInformation` uses the authenticated product identity and driver parameter-name rules; its normalized product version and unconfirmed SQL capabilities remain `DBNull`. `ReservedWords` queries the trusted system function using normal command timeout/cancellation and transaction ownership.

`Schemas`, `Tables`, `Views` and `Columns` use permission-filtered `information_schema` views. Restrictions are ordered as `Schemas(Catalog,Schema)`, `Tables(Catalog,Schema,Table,TableType)`, `Views(Catalog,Schema,Table)`, and `Columns(Catalog,Schema,Table,Column)`. Omitted/null entries impose no filter; empty strings match empty names. Values match exact case-sensitive names, with literal `%`, `_` and quotes, using bound parameters. `Tables` includes the server's reported table kinds, including views; `Views` also reports nullable definitions and an `IS_UPDATABLE` Boolean. `Columns` reports ordinal, type/UDT/domain/collation identity, nullable defaults, an `IS_NULLABLE` Boolean and server-derived lengths/precision/scale. Inapplicable or hidden facts stay `DBNull`. The existing 1,024-row exchange limit applies without truncation; use restrictions for large catalogs.

Relational collections report catalog facts for visible owning tables, excluding other sessions' temporary tables. `PrimaryKeys`/`UniqueKeys` return one row per ordered constraint column; `ForeignKeys` reports actions, deferral and the actual referenced unique index, while `ForeignKeyColumns` preserves ordered source/target pairs. Restrictions are `(Catalog,Schema,Table,Constraint)`, with a fifth `Column` for `ForeignKeyColumns`. `Indexes`/`IndexColumns` use `(Catalog,Schema,Table,Index[,Column])`. Index metadata preserves expressions, predicates, INCLUDE columns, collation and operator-class identity. Expression columns have a null `COLUMN_NAME`; sort/null-order flags are known only for btree key columns and stay `DBNull` for INCLUDE columns and other methods. Referenced-table privileges are not implied by visible foreign-key metadata. `Constraints(Catalog,Schema,Table,Constraint)` reports table constraint codes, known type names, deferral/validation/NO INHERIT flags and server definitions. `ConstraintColumns` appends a Column restriction and reports the catalog column slots in numeric order, retaining repeated columns and gaps for omitted expression slots. Constant CHECK constraints have no column rows. Unknown codes keep their raw value and a null friendly type; column NOT NULL attributes never synthesize constraint rows. Definitions are preserved without parsing or execution. Domain constraints are reported separately by `DomainConstraints`.

`Sequences(Catalog,Schema,Sequence)` includes accessible ordinary and identity-owned sequences, excluding other sessions' temporary objects. It reports type/precision, signed `Int64` start/minimum/maximum/increment, cycle and cache size without reading or advancing sequence state. `Columns` also reports `IS_IDENTITY`, identity generation/options, `IS_GENERATED` and `GENERATION_EXPRESSION`. A `nextval` or other default stays a default; generation attributes come from catalog facts. Identity values use signed `Int64`; inapplicable identity cycle and unavailable generation facts remain `DBNull`. `IS_GENERATED` preserves the server's `ALWAYS`/`NEVER` text. The case-insensitive aliases `Schemata` and `PrimaryKey` return canonical `Schemas` and `PrimaryKeys` tables with the same restrictions; both aliases are discoverable in `MetaDataCollections` and `Restrictions` with canonical restriction order. Reader metadata enrichment and other compatibility modes remain pending.

`Databases(Database)` lists readable cluster catalog rows, including templates and databases with connections disabled. It reports owner, encoding, collation/ctype, template/availability flags, signed `Int32` connection limit and a separate `HAS_CONNECT_PRIVILEGE` flag; a CONNECT grant does not establish login success. `Users(User)` lists login roles from the public role view with declared superuser/inheritance/create-role/create-database/replication/RLS-bypass flags and connection limits. Passwords, hashes, ACLs, expiration and role configuration are excluded. These collections use the same exact bound filters and exchange limits. Negative server limit sentinels are preserved. The directory contains 27 canonical collections plus two aliases, with 87 restriction descriptors.

`Functions` and `Procedures` use `(Catalog,Schema,Routine,SpecificName)` restrictions; `ProcedureParameters` adds `Parameter` and covers both kinds. Ordinary functions/procedures retain overloads through opaque `SPECIFIC_NAME` identities; aggregates/window functions are excluded. Return type/UDT, language, set-returning/strictness/security attributes and input/default counts come from server catalog facts. Parameter rows preserve numeric declared slots, unnamed names, IN/OUT/INOUT modes and distinct VARIADIC/TABLE flags. Scalar returns have no synthetic parameter row. Unknown type limits and hidden default text stay `DBNull`; a null default does not establish that no default exists. These collections use permission-filtered views, exclude other sessions' temporary objects, and share exact filters and the 1,024-row exchange limit. Restrict large catalogs. Discovery does not execute routines or enable `CommandType.StoredProcedure`/`DeriveParameters`; those APIs and package semantics remain pending.

`UserDefinedTypes(Catalog,Schema,Type)` lists visible defined enums, domains and standalone composites, excluding automatic table/view row types and generated arrays. Domains report their base type, default, nullability and available length/precision/collation facts; other kinds leave those fields null. `TypeAttributes` appends an `Attribute` restriction and preserves declared member types and numeric positions, including gaps left by dropped attributes. `EnumLabels` appends `Label`; empty labels are valid, and numeric ordinals preserve server enum order after BEFORE/AFTER insertions. A label restriction retains its full-type ordinal. `DomainConstraints` appends `Constraint` and reports actual constraint flags and unparsed definitions; definitions require the owning role, while type USAGE alone can expose the remaining metadata. Domain NOT NULL does not create a synthetic constraint row. These collections exclude other sessions' temporary schemas and share exact bound filters and exchange limits. Type discovery does not enable enum/domain/composite value codecs or CLR mappings.

await connection.OpenAsync();

command.Parameters.AddWithValue("amount", 1.2300m);

The default TLS mode verifies the server certificate and hostname using platform trust. For a private CA, add `Root Certificate=/path/to/root-ca.crt` with `SSL Mode=VerifyFull`. The file can contain a DER CA certificate or a PEM CA bundle with self-issued roots and optional intermediates; it replaces the allowed trust anchors without changing OS trust stores. Files are read on physical connection creation, so pooled reuse keeps its existing TLS session; clear the pool when new sessions must load a changed file. Invalid/missing files reject before TCP. Root Certificate with Require/Disable rejects instead of ignoring the setting. Revocation checking remains disabled. TLS policy has simulation coverage; the initial bounded live tests do not establish real-server certificate acceptance.

The PG authentication path supports server-requested password/MD5 and SCRAM-SHA-256. SCRAM verifies the extended nonce and server signature before accepting authentication, applies the PG SASLprep/raw-password profile, and bounds server iterations to 1..1,000,000, SASL payloads to 16 KiB and salt to 1 KiB. SCRAM-SHA-256-PLUS/channel binding and SM3 algorithms remain pending; a PLUS-only offer rejects. Standard protocol vectors and loopback logins do not establish real Kingbase password-policy compatibility.

`KingbaseDataReader` buffers completed PG results with exact typed/provider numeric access, binary/text slices and column metadata. `GetColumnSchema` and `GetSchemaTable` report declared VARCHAR/CHAR character lengths and NUMERIC precision/scale from recognized PG type modifiers, independently of NULL values or empty results. Unconstrained or unrecognized modifiers remain unknown. Signed scale is preserved by the metadata decoder; the currently tested server rejects negative-scale and scale-greater-than-precision declarations. A connection owns its returned Reader until close. Default, SchemaOnly, KeyInfo, CloseConnection, SingleRow and SingleResult behaviors have bounded PG support; raw PG identities remain available in `GetSchemaTable` provider columns. Streaming/SequentialAccess and system transactions remain pending.

PG `ExecuteReader(CommandBehavior.SchemaOnly)` and its asynchronous counterpart describe one statement using Parse/Describe/Sync. SQL and parameter bindings are validated, but parameter values and Bind/Execute frames are not sent. The Reader exposes supported column types/facets with no rows and RecordsAffected=-1; statements without output still produce an empty result. The same behavior works for sequential batches, whose commands remain NotExecuted with RecordsAffected=-1. Describing transaction-control SQL does not end the local transaction. Existing named prepared handles remain usable, and description requests do not count toward automatic preparation. Server parsing/permission errors are returned; malformed or interrupted exchanges retire the physical connection.

PG `KeyInfo`, including `SchemaOnly` and prepared/sequential batch requests, loads visible base names through bound catalog lookups. Proven direct single-table projections additionally expose nullability, complete immediate non-null primary/unique keys with compatible equality semantics, identity, canonical owned-sequence defaults and structural read-only facts. No hidden columns are added. Joins, views, set-returning expressions and unproven shapes retain unknown guarantees; ordinary inheritance needs `ONLY`. Read-only metadata describes generated/ALWAYS identity columns, not current write privileges. Under Repeatable Read/Serializable, base names and guarantees remain unknown because catalog snapshots can lag relation lookup. Description and catalog reads bracket the original operation; observed descriptor/catalog drift fails without replay, preserving acknowledged batch outcomes. Metadata shares the buffered byte budget. Other modes and complete Reader metadata acceptance remain open.

`KingbaseDataAdapter` derives from `DbDataAdapter` and supports bounded PG DataTable/DataSet Fill, FillSchema and Update with explicitly supplied Select/Insert/Update/Delete commands. Set parameter SourceColumn and SourceVersion for current/original values and supply explicit types for NULL input; include original values in WHERE clauses for optimistic concurrency. Typed RowUpdating/RowUpdated events support command replacement, skipping and error handling. BCL mappings, accept-change policies, returned records and ContinueUpdateOnError apply. An adapter closes a connection only when it opened it for that operation; commands/connections remain caller-owned. Fill still uses the driver's existing buffered limits. PG command generation is described below; streaming and full mode/platform acceptance remain pending.

`UpdateBatchSize` defaults to 1. Set it to a larger nonnegative value to stage row commands, or 0 to stage all eligible rows; memory grows with the selected logical batch. For batched updates, set each write command's `UpdatedRowSource = UpdateRowSource.None`; `FirstReturnedRecord` is unsupported. RowUpdating handlers run before SQL/parameter snapshots, including byte-array copies. One logical batch requires the same connection, transaction and command timeout, and executes sequential physical groups of at most 256 commands under one timeout budget. This is not wire pipelining. Failure stops that batch without replay; ContinueUpdateOnError may allow later logical batches after synchronization. Positively acknowledged rows retain their results, while failed, unknown and unsent rows remain pending with errors. Acknowledgment does not establish transaction commit: use an explicit transaction when atomicity is required.

`KingbaseCommandBuilder` derives from `DbCommandBuilder`, generates PG INSERT/UPDATE/DELETE commands and attaches to a KingbaseDataAdapter for automatic row updates. It requires proven, distinct direct-table columns and a complete compatible key for update/delete. Generated SQL preserves quoted names, aliases, typed NULLs, original-value concurrency and explicit transactions; identity/generated fields are excluded from writes. Identifiers use native `U&"..."` quoting, including quote/backslash escapes. Column-derived parameter names use bounded ASCII hashes. RefreshSchema refreshes metadata and parameter-name caches, including through BCL references. ONLY/inherited, repeated-column, complex-query and snapshot-isolated unknown projections explicitly reject generation. XML/JSON values bind for writes but are excluded from equality predicates because PG lacks their equality operators; changes only to those values are not concurrency checks. Keep UTC DateTime columns in DataTables configured with DateTimeMode=Utc before loading TIMESTAMPTZ values. Other modes and full M08 acceptance remain open.

PG DATE maps to an Unspecified midnight `DateTime`. Use `KingbaseDbType.Date`, `DbType.Date` or `DataTypeName="pg_catalog.date"` for explicit binding; DateTime input must have no time component and Kind Unspecified. `KingbaseDate` is inferred as DATE on every asset; modern assets also infer `DateOnly` and support `GetFieldValue<DateOnly>`. Unspecified DateTime infers TIMESTAMP and UTC DateTime infers TIMESTAMPTZ; select DATE explicitly when needed. DATE results require confirmed ISO DateStyle (`ISO, MDY`, `ISO, DMY` or `ISO, YMD`); unsupported or unknown output styles reject conversion. Use application SQL to select a supported style when necessary.

`reader.GetFieldValue<KingbaseDate>(ordinal)` or `GetProviderSpecificValue` preserves BC dates, years outside the CLR range and explicit `infinity` / `-infinity`. Default DateTime/DateOnly conversion throws OverflowException for these values. For example, `KingbaseDate.Parse("0001-02-29 BC")` preserves a leap day in 1 BC; negative constructor years mean BC, with no year zero. The immutable value uses the proleptic Gregorian calendar, defaults to 0001-01-01 and accepts absolute years up to seven digits; each server still enforces its own range. No timezone conversion, date truncation or MinValue/MaxValue infinity substitution occurs.

PG TIME uses `TimeSpan` from zero through 24 hours inclusive at exact microsecond precision. Specify `DbType.Time`, `KingbaseDbType.Time` or `DataTypeName="pg_catalog.time"` for TimeSpan TIME input; otherwise TimeSpan infers INTERVAL. Modern assets infer `TimeOnly` and support `GetFieldValue<TimeOnly>`; reading `24:00:00` as TimeOnly throws OverflowException. Extra submicrosecond ticks reject instead of rounding. Numeric TIME/TIMETZ text does not depend on DateStyle or session TimeZone.

PG TIMETZ uses immutable `KingbaseTimeTz` as both its default and provider value, inferred on every asset. For example, `KingbaseTimeTz.Parse("12:34:56.123456+05:30:01")` preserves microseconds and an offset with seconds. Its `Time` is the wall-clock TimeSpan and `Offset` is signed east of UTC, in whole seconds with magnitude below 16 hours. Default is midnight at offset zero. Equality compares both components exactly; no date, local timezone or UTC normalization is introduced. Bind explicitly using `KingbaseDbType.TimeTz` or `pg_catalog.timetz`; DbType.Time is compatible with an explicit TIMETZ selection but selects TIME alone. TimeSpan/TimeOnly/DateTimeOffset cannot silently discard or manufacture the offset. Binary temporal formats and other modes' temporal types remain pending.

PG TIMESTAMP uses Unspecified `DateTime`; TIMESTAMPTZ uses UTC `DateTime`. Input inference follows Kind; Local DateTime rejects instead of applying the machine timezone or DST. DateTimeOffset infers TIMESTAMPTZ and normalizes its explicit offset to UTC. Select types explicitly using `KingbaseDbType.Timestamp`/`TimestampTz`, the corresponding `pg_catalog` type name, or `DbType.DateTime`/`DateTime2` (TIMESTAMP) and `DbType.DateTimeOffset` (TIMESTAMPTZ). All inputs require exact microseconds. TIMESTAMP finite clock values must be below 24 hours.

Use `GetFieldValue<KingbaseTimestamp>` or `GetFieldValue<KingbaseTimestampTz>` for lossless BC/out-of-CLR-year/infinity access. KingbaseTimestamp stores a finite `KingbaseDate` plus `TimeSpan`, or explicit infinity; KingbaseTimestampTz stores its UTC calendar timestamp in `UtcValue`. For example, `KingbaseTimestampTz.Parse("2024-03-01 00:00:00+01")` formats as `2024-02-29 23:00:00+00`. Both defaults represent 0001-01-01 midnight; the zoned value is UTC. Bounded proleptic Gregorian parsing preserves the BC/AD transition without year zero. Infinity and non-CLR conversions throw OverflowException. `GetFieldValue<DateTimeOffset>` applies only to TIMESTAMPTZ and returns offset zero. Strict ISO DateStyle confirmation is required for non-NULL timestamp results; TIMESTAMPTZ additionally requires numeric offset text and normalizes each value to UTC, independently of later session timezone changes. Non-ISO styles reject conversion until the application selects ISO.

PG INTERVAL uses `KingbaseInterval` as both its stable default and provider value. `new KingbaseInterval(14, -3, -1)` preserves independent months, days and clock microseconds and formats as `P14M-3DT-0.000001S`. It infers INTERVAL, as does exact-microsecond `TimeSpan`; select `KingbaseDbType.Interval` or `pg_catalog.interval` explicitly for typed NULL. Inferred or provider-enum selection reports `DbType.Object`; a NULL selected solely by DataTypeName retains the existing `DbType.String` fallback. Setting DbType.Object does not select a provider-specific interval type. `GetFieldValue<TimeSpan>` requires zero months and a combined day/clock duration within the CLR range; months are never guessed as a number of days. Provider access survives conversion failures.

INTERVAL results require a confirmed per-result IntervalStyle: postgres/kingbase, postgres_verbose/kingbase_verbose, sql_standard or iso_8601. Mixed signs and verbose `ago` are preserved independently of DateStyle, TimeZone and later style changes. Public Parse/TryParse accepts bounded ISO duration fields; extra fractional precision rejects. Client field bounds do not promise server text bounds: the tested server rejects full Int64 clock extremes (22015) and emits noncanonical minimum-day verbose output, which rejects safely; select ISO output for that boundary. Binary/full-range interval acceptance, Oracle YM/DS and other-mode aliases remain open.

Use `connection.CreateBatch()` or `new KingbaseBatch(connection, transaction)` for sequential PG-wire statements in the detected compatibility mode. Modern assets derive from `DbBatch`; Standard assets expose the same typed API without that unavailable base class. Each `KingbaseBatchCommand` has its own parameters. One `Timeout` covers the entire operation (connection command timeout by default; zero disables it). `Prepare`/`PrepareAsync` prepares the statements sequentially; execution also honors opt-in automatic preparation. No implicit transaction or retry is introduced. Non-PG mode acceptance remains bounded as described above.

```csharp
using var batch = connection.CreateBatch();
var first = new KingbaseBatchCommand("SELECT @p");
first.Parameters.AddWithValue("p", 41);
batch.BatchCommands.Add(first);
batch.BatchCommands.Add(new KingbaseBatchCommand("SELECT 42"));
using var reader = await batch.ExecuteReaderAsync();
// Read each result in order with Read/NextResult.
```

Execution stops at the first error. `FailedCommandIndex` identifies that zero-based command; `KingbaseException.BatchCommand` identifies a server-rejected command. Inspect each command's `ExecutionStatus` and `RecordsAffected`: NotExecuted means it was never reached, Succeeded means its exchange was acknowledged, Failed means local validation/preparation or conclusive server rejection, and OutcomeUnknown means an Execute/Query frame was attempted without a conclusive outcome, including a synchronized SQLSTATE 40003. Successful execution does not imply transaction commit; caller-managed rollback remains explicit. An explicitly assigned transaction is checked before every statement; ending it stops subsequent execution. Earlier statements can persist when no explicit transaction is used. Each non-reentrant Execute resets counts/statuses before preflight validation, and acknowledged successes/counts remain visible if later metadata, buffering or CLR conversion fails. Preparation does not mark statements executed. Parameters are snapshotted when each statement is reached; concurrent mutation is unsupported.

A batch accepts at most 256 statements and buffers at most 256 results, 1024 rows, 1024 columns and 1 MiB of text/metadata across all statements. A post-acknowledgment capacity failure stops before the next statement. The Reader retains connection ownership until closed. ExecuteScalar validates the first scalar when reached, executes remaining statements if conversion succeeds, and returns that scalar; conversion failure identifies the acknowledged command and stops before later SQL. Reader getter conversion remains lazy. SingleResult/SingleRow restrict Reader visibility without skipping later execution. Streaming, other compatibility modes and pipelined execution remain pending.

PG commands support `Prepare()` / `PrepareAsync(token)` and `Unprepare()` / `UnprepareAsync(token)`:

```csharp
await command.PrepareAsync();
command.Parameters[0].Value = 2.50m;
var nextAmount = await command.ExecuteScalarAsync();
await command.UnprepareAsync();
```

Preparation validates current SQL and catalog-bound input types; typed NULL is supported. Value changes reuse the statement. SQL/type/lexical changes, eviction, pool reset or reconnection detach stale handles before execution. Unprepare closes the attached shared physical handle, so another command using it also detaches. Edits/disposal detach without network I/O; cached server resources stay within the physical session's 64-statement/1 MiB limit. Controls use CommandTimeout, caller cancellation and Cancel, and reject an active Reader. Server preparation/schema errors are returned without replay; callers can explicitly prepare a replacement. The live suite records bounded PG schema-error and transaction-recovery evidence; other modes and platforms remain unaccepted.

Automatic PG preparation is opt-in: set `Max Auto Prepare=16;Auto Prepare Min Usages=5` (or the builder properties `MaxAutoPrepare` / `AutoPrepareMinUsages`). The maximum defaults to 0 (disabled) and accepts 0..64; the usage threshold defaults to 5 and accepts 1..Int32.MaxValue. Successful unnamed protocol exchanges with the same SQL, ordered actual types and lexical state count per physical session, across command objects. The threshold execution prepares first; value changes reuse its handle. Candidates retain no values/schema and are bounded at 128 entries/1 MiB of encoded signatures, separately from the global prepared limits. Automatic capacity evicts the least recently used automatic statement with acknowledged Close. Manual Prepare promotes a shared automatic entry to explicit ownership; the global physical limit can still evict it. Unprepare of an attached handle, plan-invalidating errors and pool reset restart the relevant usage counts. Unprepare before a handle is attached is a no-op and retains candidate counts. An automatic handle attaches before execution, so Unprepare can close it even after its first execution returns a synchronized SQL error. A subsequent caller request may prepare again at its threshold; a failed request is never replayed. With automatic preparation disabled, detached execution uses ordinary binding until explicitly prepared again. Managed transaction controls remain unnamed. Sequential batch execution uses the same preparation cache.

Local `KingbaseTransaction` supports synchronous/asynchronous Begin, Commit, Rollback and savepoints on the initial PG path:

```csharp
using var transaction = await connection.BeginTransactionAsync();
await transaction.SaveAsync("before_update");
using var update = new KingbaseCommand("UPDATE items SET amount=:amount WHERE id=:id", connection)
    { Transaction = transaction };
update.Parameters.AddWithValue("amount", 12.50m);
update.Parameters.AddWithValue("id", 1);
await update.ExecuteNonQueryAsync();
await transaction.ReleaseAsync("before_update");
await transaction.CommitAsync();
```

The default/Unspecified explicitly requests ReadCommitted; RepeatableRead and Serializable send their exact PG isolation keywords. ReadUncommitted, Snapshot and Chaos reject without mapping to another level. The transaction's `IsolationLevel` records its Begin request, with Unspecified normalized to ReadCommitted; later application SQL can change server characteristics independently. A null Command.Transaction participates in the connection's current transaction; an explicit reference must be its active transaction. Close or a broken session invalidates that owner. A COMMIT acknowledged as ROLLBACK fails explicitly. `KingbaseTransactionException.OutcomeUnknown` and `KingbaseTransaction.OutcomeUnknown` identify uncertain commits; cancellation remains `OperationCanceledException` with uncertainty available on the transaction. Never automatically replay an uncertain transaction. Disposal attempts rollback within five seconds, then closes its still-owned connection if cleanup cannot synchronize. These paths have loopback evidence; server isolation semantics remain unaccepted.

For a transaction-scoped read-only request, use the explicit access-mode overload:

```csharp
using var readOnly = await connection.BeginTransactionAsync(
    System.Data.IsolationLevel.RepeatableRead, readOnly: true);
// Execute reads here. Read-only restrictions are enforced by the server.
await readOnly.CommitAsync();
```

The synchronous counterpart is `BeginTransaction(isolationLevel, readOnly)`. Explicit true/false sends READ ONLY/READ WRITE in the same BEGIN; existing overloads omit the access mode and honor the session's read-only default. The driver neither changes session defaults nor filters application SQL to simulate read-only enforcement. Real concurrent-read, serialization and write-rejection behavior still requires Kingbase acceptance.

Use `Save(name)`, `Rollback(name)` and `Release(name)` or their asynchronous counterparts for savepoints; `Rollback(name)` keeps the transaction active. Names preserve case and whitespace, escape double quotes, and reject empty/NUL/invalid Unicode or names exceeding the reported UTF-8 byte limit. The first managed Begin on each physical session reads `SHOW max_identifier_length` under the command deadline; that query and savepoint effects remain subject to real Kingbase acceptance. Repeated names and savepoints created through SQL are resolved by the server. Modern assets override the BCL savepoint APIs; Standard assets expose the same typed methods.

`KingbaseDataSourceBuilder.Build()` snapshots validated configuration. Its source creates independent connections with immutable configuration and redacted connection strings. Disposing the source rejects new opens and reopening, cancels pending opens, and lets already-open connections and Readers finish. Modern assets derive from `DbDataSource`; Standard assets expose typed creation/open methods.

Ordinary PG pooling now gives each DataSource a private pool; direct connections share pools with normalized configuration. Maximum Pool Size counts opening, leased, resetting and retiring sessions. One Open timeout covers FIFO waiting, initialization and idle validation. Close/CloseAsync revokes children, rolls back unfinished local transactions, issues DISCARD ALL, restores bound settings and verifies identity/catalog/state within Cleanup Timeout; failed cleanup retires the socket. Active interrupted commands retire their sessions. Clear with `KingbaseConnection.ClearPool(connection)`, `KingbaseConnection.ClearAllPools()` or `source.ClearPool()`; active leases finish and retire on return. Idle/total lifetime expiry and a lazy minimum are implemented. These paths have loopback coverage and bounded PG same-session/settings-restoration LIVE evidence. Complete resource cleanup/load, transaction reservations and other backends remain open.

A DataSource can obtain fresh credentials through `builder.PasswordProvider`, a `Task<string>` delegate receiving immutable endpoint metadata and a cancellation token. Configure it without an explicit Password; Build and DI resolution remain lazy. Each new physical initialization invokes it under the Open budget, while idle reuse and ordinary reset do not. Clear the pool to retire existing sessions and fetch a new password on replacement. Concurrent callbacks must be supported; cancelled external work may finish later, but cannot open a socket or publish a lease. Provider failures use safe `KingbasePasswordProviderException` text without retaining the original exception. The existing DI builder configuration callback accepts this property too.
The separate `KingbaseConnector.DependencyInjection` package provides closed transient connections and lazy singleton DataSources:

```csharp
using Microsoft.Extensions.DependencyInjection;

var services = new ServiceCollection();
services.AddKingbaseDataSource(
    "Host=localhost;Database=app;Username=user;Password=secret");
using var provider = services.BuildServiceProvider();
var source = provider.GetRequiredService<KingbaseDataSource>();
using var connection = await source.OpenConnectionAsync();
```

Use `AddKingbaseConnection` for transient connections, or `AddKeyedKingbaseDataSource` for multiple keyed sources on modern assets. Unkeyed BCL aliases are added when absent; duplicate provider/key registrations reject atomically. The container owns resolved services. DI uses Microsoft.Extensions lower-bound ranges `[8.0.0,)` on net8.0, `[9.0.0,)` on net9.0, and `[10.0.0,)` on net10.0 and Standard assets. DataSources use private pools by default; direct DataSource commands remain future work.
