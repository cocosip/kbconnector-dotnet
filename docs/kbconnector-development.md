# KingbaseConnector Development Guide

Baseline date: 2026-11-23. Last updated: 2026-11-24. This guide describes how to implement the [unified design](kbconnector-design.md) and [feature matrix](kbconnector-feature-matrix.md). The [progress tracker](kbconnector-development-progress.md) owns current implementation and validation status.

The initial documentation baseline had no product projects. DP01 now provides the solution, core project, test projects, and local verification entry point described below. The progress tracker records their exact acceptance boundary; engineering completion does not establish working database functionality.

## 1. Development boundaries

- Build one independent managed ADO.NET core for KingbaseES. Implement V9 first, then extend the same core to the agreed V8 targets, starting with V8R6C9B14.
- Cover the PG, Oracle, MySQL, and SQL Server compatibility modes and actual available deployment combinations through the default Kingbase PG v3-style connection path; this remains the normal path for every mode. CompatibilityMode defaults to Auto: after authentication, obtain the mode through the selected backend's verified bootstrap (PG server parameters/SHOW database_mode, or separately established MySQL endpoint queries) before loading mode-dependent catalogs/codecs. An explicit CompatibilityMode selects driver rules; reject a conflicting server-reported mode without changing the protocol or server mode. Keep configured, effective, and server-reported identities distinct, include the selection policy in pool identity, and load actual required catalog metadata in either path. Ordinary application SQL remains the caller's responsibility; adapt the SQL generated by the driver and, later, the separate EF provider.
- Register protocol availability with each profile. Add the explicit WireProtocol=MySql backend for exceptional deployments exposing only MySQL, with an explicit port and independent handshake/authentication/execution/type/reset acceptance. Keep the default PostgreSql, with no protocol Auto, sniffing, switching, or port fallback. MySQL wire initially supports MySql mode only. CompatibilityMode does not select a protocol.
- Implement built-in pooling in the provider, shared management with protocol-isolated sessions. Section 9 of the design defines normalized/direct versus private DataSource ownership, proposed defaults, hard capacity, cancellation/cleanup, per-backend reset, clear generations, disposal, credential rotation, and diagnostics. A new logical connection is not a new physical login when pooling can safely reuse it.
- Keep official DLLs and decompiled code out of product source and packages. Use official binaries only as isolated comparison subjects; record their complete hashes when they inform a contract.
- Preserve all matrix IDs and scope categories. A conditional feature requires an explicit applicability decision. Missing infrastructure is pending validation, not a server limitation or a client defect.
- Keep EF Core providers independent and subsequent to the ADO.NET foundation. Do not add EF runtime dependencies to the core.
- Write documentation, API descriptions, and progress updates in English. Temporary walkthroughs and review reports belong outside the repository.

The design and matrix are the development baseline. Their explicit proposals remain proposals; settle an API or default before implementing its affected contract and update the owning document in the same change. Unknown server facts U01-U07 remain discovery tasks, with the impact already described in design section 13. They do not block unrelated engineering, framing, or codec work.

## 3. Delivery order and dependencies

Phase definitions and release gates remain in design sections 11 and 12. The tracker breaks them into independently completable work packages. A feature spanning phases is complete only after all of its applicable requirements are satisfied; an early subset must be labeled as a subset.

| Phase | Primary work | Dependency and exit condition |
| --- | --- | --- |
| V9-0 | Register real profiles; establish version/mode queries, directory facts, and routine output behavior. | Establish evidence for each server-dependent rule before claiming that rule works. Discovery can run alongside foundational engineering. |
| V9-1 | Engineering, transport, framing, authentication, identity, basic types, parameters, Reader, local transactions, basic pooling, and metadata. | Produce a usable minimum path and its failure handling. This phase does not constitute complete V9 support. |
| V9-2 | Remaining types, routines/output/cursors, Prepare, batch, COPY/LOB, schema, mapping, modern APIs, and the exceptional MySQL backend (DP20-DP21). | Close required functional scope and decide applicability of conditional features. |
| V9-3 | Deployment/version acceptance, failover, advanced authentication/transactions, both-protocol pool/reset and exceptional MySQL-only acceptance (DP22), resource/fault testing, package consumers, and release preparation. | Satisfy the V9 release gate using actual profile and test evidence. |
| V8-1 | V8R6C9B14 identity, catalogs, modes, types, authentication, and routine differences. | Add only verified differences to the shared core and execute the applicable matrix paths. |
| V8-2 | Other agreed V8 builds and V9 regression. | Publish an explicit tested support set without regressing accepted V9 profiles. |
| EF follow-up | Separate EF Core 8/9/10 providers, offline dialect profiles, SQL translation, migrations, and reverse engineering. | Establish a separate provider design and matrix after the ADO.NET contracts are stable. |

Build transport and framing before dependent execution state machines. Identity initialization needs an explicit text bootstrap path, then a verified catalog query, then typed codecs; avoid making full codec loading a prerequisite for mode detection. DP20 includes bounded COM_QUERY/text decoding for native bootstrap only, so it does not depend on the complete typed execution delivered by DP21. Implement command/Reader ownership and error synchronization before adding pool reuse. Routines and parameter derivation depend on reliable type and schema metadata. COPY and notification waiting must reuse the session ownership rules. High availability must reuse initialization per new physical endpoint.

A practical first sequence is DP01 (engineering), DP02 (profile discovery) in parallel where environments permit, then DP03-DP07 (connection through basic pooling). Each package has its own completion checklist in the tracker. Later packages may begin once their documented prerequisites are satisfied; discovery work need not serialize unrelated implementation.

DP07 first establishes shared pool management and PG cleanup. DP20 adds the explicit native MySQL session backend after DP01/DP03 foundations; DP21 adds its execution/type/schema paths after DP20 and the shared public contracts. DP22 validates pool reset, cancellation, resources, and MySQL-only operation after DP07/DP20/DP21. DP16 cannot close the V9 gate without these applicable results. Work-package IDs remain stable and are not a chronological ordering.

Keep protocol-specific features explicitly scoped. Do not route MySQL wire through PG OIDs, ReadyForQuery, COPY, or CancelRequest. A MySQL handshake alone is not Kingbase identity/mode proof. U07 must resolve native bootstrap/reset/cancel details; unavailable safe reset means physical retirement, not reuse without cleaning. Add deterministic pool races and two-borrower state-isolation cases for each backend before claiming shared pooling works. For accepted X04 profiles, implement same-transaction pending-session reacquisition before ordinary pool waiting and test sequential opens at maximum size 1. Keep reserved sessions counted and invalidate old logical leases. PG cancellation must await the bounded cancellation-channel closure barrier; lexical plan caches must include the verified session quote/escape settings.

### 3.1 Startup decisions and the first usable increment

The existing baseline is sufficient to start DP01 and independent DP03/DP04 foundations. Settle the decisions below before implementing the affected contract. Record the selected contract in its owning design section and the decision/evidence in the mapped work package; the table is a dependency checklist, not another progress ledger. A proposal is not frozen merely because a test was written around it.

| Decision or evidence | Needed before | Minimum recorded result |
| --- | --- | --- |
| Engineering toolchain and test entry points | Closing DP01 | Exact SDK, test runner and dependency versions; restore/build/test commands; intended host and asset selection for each product TFM; a reproducible clean-checkout check. |
| First public API and configuration slice | Implementing the corresponding DP03/DP06 surface | Connection/configuration-builder, command, parameter, Reader and exception signatures for the slice; TFM differences; keyword aliases, units, defaults and invalid-value behavior. Include CompatibilityMode, WireProtocol, TLS, Open/command/cleanup timeout semantics, and pooling settings. Keep SQLSTATE, cancellation versus timeout, and uncertain execution outcomes distinguishable. |
| First real V9 PG profile and bootstrap facts | Accepting DP03 identity or the first live increment | Register an available actual V9 PG profile in tracker section 5. Retain the full-version query and raw result, mode source, required catalog and lexical/codec settings, and auth/TLS facts. Resolve the affected U01/U02 subset; do not invent a product version or mode to make Open pass. |
| Safe PG reset and physical reuse | Accepting the DP07 pool subset | Profile-specific reset sequence, baseline restoration and prepared-cache policy, plus evidence from two logical borrowers of the same physical session. If only physical retirement is safe, record that limit and keep reuse acceptance pending. |
| Executable validation and live opt-in | Adding the corresponding test suite | Named tests linked to feature/subcase IDs, exact runner/filter commands, private profile configuration and read/write opt-in names, visible skip/failure behavior, and test-owned cleanup. Ordinary unit/protocol execution remains offline. |
| Reference-code and dependency provenance | Introducing source or a dependency | Record the relevant source/reference identity and dependency/license choice. Keep official DLL comparison isolated and implement independently. U06 package/publication decisions must be resolved before public release. |

DP01 may use the documented provisional project/package identifiers; record the choice and keep public package identity explicitly provisional until U06 is resolved. Select concrete versions and test hosts during setup from the available verified environment rather than treating this guide as an executable lockfile. Extend the public contract incrementally when later features begin; the first slice need not freeze every future type or routine API.

Deliver the first usable PG increment through existing work packages:

1. **DP01:** create the shared build/package structure and offline test entry points; prove all intended product assets build. Keep unavailable runtime-host acceptance pending.
2. **DP02 with DP03/DP04:** establish the first actual profile, initialization and ownership contracts; verify framing, authentication, identity, cancellation and failure synchronization with controlled peers and the applicable live cases.
3. **DP05/DP06 with the local X01 subset of DP10:** open a connection, execute a parameterized query with typed NULL and basic integer/text/binary results, close a Reader, and demonstrate local rollback on the registered profile. Add trailing-error and timeout/cancellation cases that prove synchronization or physical retirement.
4. **DP07:** demonstrate two sequential logical borrowers, actual physical reuse with verified reset, bounded capacity/wait cancellation, and rejection of access through an old logical resource. Record reset state isolation and remaining pool subfeatures explicitly.

The increment is accepted only for its named feature subsets and recorded profile. It does not close V9-1 or establish all-mode, all-version, advanced-type, routine, failover, or native MySQL acceptance. Keep the corresponding parent rows open until their complete requirements pass. The exceptional MySQL work remains DP20-DP22 and remains part of the V9 gate; the normal PG path can advance while U07 is investigated.

U01/U02 gate server identity and live acceptance; they do not gate independent engineering, framing, parser or codec tests. U03 gates the affected routine paths, U04 the subsequent V8 work, U05 the affected conditional capabilities, and U07 native-endpoint behavior. Missing evidence never permits a permissive runtime fallback. The tracker remains the place to record which dependency is actually blocking a unit.

## 4. Work on one functional unit

1. Select a tracker work package and its matrix IDs. Read the full feature contract, applicable acceptance groups, and relevant source evidence. Set its status to In progress and name the intended boundary.
2. Resolve any API/default decision needed by this unit. For server-dependent behavior, identify the target profile and evidence. If evidence is missing, record the specific dependency and continue only the independent parts.
3. Implement the smallest complete public path, including callers, configuration, ownership, failure behavior, metadata, and applicable TFMs. A placeholder, unsupported-method stub, or successful happy path alone is not an implemented feature.
4. Add meaningful tests for the contract and failure cases. Use deterministic protocol peers for message, cancellation, synchronization, and resource races; add real-server cases when the behavior depends on the server.
5. Run the checks appropriate to the change. Record the exact commands, results, source revision or artifact identity, and applicable profile IDs. A skipped live test is pending, never passed.
6. Update the feature's row and evidence entry in the tracker, and revise the design/matrix if the contract changed. Mark the checkbox complete only when the completion rules below are met.

For a large feature, record named sub-items such as C07/TLS handshake or C07/certificate verification in its evidence entry. Check completed sub-items individually while leaving the parent feature open until its whole contract is satisfied. Keep the canonical feature ID unchanged.

## 5. Validation workflow

| Validation layer | What to demonstrate | Recording rule |
| --- | --- | --- |
| Unit tests | Parsers, names, encodings, numeric/date boundaries, mapping, and configuration behavior. | Include the targeted test names and meaningful boundary cases. |
| Protocol simulation (SIM) | Message fragmentation, framing limits, authentication challenges, cancellation races, synchronization, leases, and resource recovery. | Record Passed only for executed cases; identify simulation limits. |
| Official comparison | The same inputs against an identified official DLL and server. | Run comparison DLLs in separate processes; use independent evidence to resolve disagreements. |
| Live acceptance (LIVE) | Actual version/deployment/mode behavior, catalogs, authentication, routines, types, and server state. | Record the complete profile identity and feature/subcase results; do not generalize to untested profiles. |
| Package consumers | The actual package asset for every target framework and supported host. | Prove the resolved asset; a modern asset selected automatically does not validate a Standard asset. |
| Fault/resource tests | Broken links, partial responses, cancellation, pool exhaustion, late cleanup, uncertain writes/commits, and leaks. | Confirm outcome and resource state, not just throughput or absence of exceptions. |

After setup, the following are baseline local commands from the repository root. The selected test runner and eventual CI configuration must implement these checks or document their concrete equivalent:

```powershell
dotnet --info
dotnet restore KingbaseConnector.slnx
dotnet build KingbaseConnector.slnx -c Release --no-restore
dotnet test tests/KingbaseConnector.UnitTests -c Release --no-restore
dotnet test tests/KingbaseConnector.ProtocolTests -c Release --no-restore
dotnet pack src/KingbaseConnector -c Release --no-build -o artifacts/packages
```

The executable aggregate entry point is `./eng/verify.ps1` (PowerShell 7). It restores/builds the solution, runs tests, packs, and validates all five explicit package assets using fresh per-run package caches and consumer outputs. SDK 10.0.403 is pinned without roll-forward. Unit/protocol/integration projects use VSTest (`Microsoft.NET.Test.Sdk` 18.0.1, MIT), xUnit 2.9.3 (Apache-2.0), and `xunit.runner.visualstudio` 3.1.5 (Apache-2.0) on net8.0/net9.0/net10.0; these test-only dependencies do not flow into the core package. Licenses were checked in the restored package nuspecs. The core initially has no explicit runtime package dependencies; the netstandard2.0 SDK reference resolves NETStandard.Library 2.0.3 and Microsoft.NETCore.Platforms 1.1.0 as build inputs.

Consumers are intentionally outside the solution: they reference the packed package, not the source project, and require packing first. `eng/verify.ps1` forces each `lib/<asset>/KingbaseConnector.dll` through a NuGet-generated package path, checks its TargetFrameworkAttribute at runtime, and runs Standard assets on .NET 8 and modern assets on their matching .NET 8/9/10 hosts. They prove assembly loading and the initial public configuration contract (canonical alias/defaults, Validate, password-safe ToString, explicit MySQL port); expand their assertions as later public APIs are implemented. Do not interpret this as complete G03 or Framework/Linux/ARM64 acceptance.

Integration entry point: `dotnet test tests/KingbaseConnector.IntegrationTests -c Release`. Without `KINGBASE_TEST_LIVE=1`, the live gate is visibly skipped. With that exact opt-in, it currently fails because no real profile or server acceptance cases are registered; it makes no network connection. Register profiles and replace the gate with real cases before claiming LIVE results. The protocol project now runs deterministic PG stream/framing and control-parser cases offline; these do not establish network or server acceptance. Ordinary test execution must never connect to a live database without explicit opt-in.

Select a test host that can execute each intended runtime. If host/asset coverage is missing, leave the corresponding G03-G05 result pending. Build success alone does not satisfy runtime consumption, TLS, operating-system, or architecture acceptance.

### Live profiles and credentials

Before live testing, register the matrix section 3.2 fields in the tracker's profile registry: full product version and query source, startup version, deployment, configured/effective/reported mode and source, selected protocol/actual endpoint, native auth/reset/cancel capabilities, database settings, authentication/TLS, topology/platform, driver artifact, test IDs, results, and cleanup status.

Store credentials in User Secrets or process environment and keep private endpoint configuration outside tracked files. Use a dedicated test schema or prefix; define cleanup for DDL that is outside a transaction. Keep discovery read-only until write tests are explicitly enabled for the test environment. Do not record passwords, private keys, full connection strings, or business data in progress evidence.

When a failure occurs, classify it as client defect, confirmed server/version/deployment limitation, permission/configuration limit, missing environment, or unknown. Include evidence for the classification. Do not retry SQL whose write/commit outcome may be uncertain, and do not treat matching official behavior as proof of correctness.

## 6. Definition of complete

The feature matrix owns the contract; the tracker owns its status. Use these meanings consistently:

| Status | Meaning | Completion checkbox |
| --- | --- | --- |
| Not started | No implementation work has begun. | Open |
| In progress | A named portion is being implemented or validated. | Open |
| Implemented | The intended code path exists and local checks pass, but some applicable acceptance remains outstanding. | Open |
| Blocked | A specific dependency prevents the next required step. Preserve implementation and test results in the evidence entry. | Open |
| Complete | The entire declared unit meets all applicable implementation and acceptance requirements below. | Checked |
| Deferred | Explicit later scope such as L, the subsequent V8 stage, or a recorded scope decision. It is not finished. | Open |
| Not applicable | Evidence establishes that the feature does not apply to a named profile or explicitly decided scope. | Open; record the decision, not a completed implementation |

A feature can be marked **Complete** and checked `[x]` when:

- Its public behavior, error paths, resource ownership, configuration, and applicable TFM/API paths are implemented with no outstanding required stubs.
- Relevant unit/SIM tests and change-specific checks pass. For a unit with no protocol simulation or server behavior, record N/A with a reason rather than inventing a pass.
- Each required live profile in the explicitly declared acceptance set has passed, or a particular validation dimension is demonstrably inapplicable and its reason is recorded. Missing servers, credentials, permissions, or unimplemented tests never justify N/A.
- The record identifies source/test evidence, results, accepted profiles, and remaining limits. Do not mark an entire four-mode feature complete from a single-mode result; track a completed subset separately.
- The documents and tracker reflect the final behavior, and there is no unresolved defect that violates this unit's contract.

Engineering-only units such as G01 can reach Complete with build/structure evidence and justified SIM/LIVE N/A. Server-facing features can reach Implemented while waiting for LIVE; their implementation progress remains visible without claiming server acceptance. No percentage of completed rows alone establishes a release.

For a work package checkbox, every required mapped feature or explicitly named subfeature must meet its package exit condition. A package such as the basic Reader path may be complete while a larger feature remains open for later type or mode coverage; identify that subset in its evidence. V9 release completion still requires every applicable R feature, an explicit decision for every C feature, and the design section 11.2 gates. Deferred and Not applicable entries never inflate the completed implementation count.

## 7. Keep progress current

Update the tracker in the same change that completes a functional unit. Replace placeholders in the evidence entry with actual paths, command outcomes, revision/artifact IDs, profile IDs, and the completion date. Update the summary counts and phase/work-package state to agree with feature rows.

If later work breaks a completed contract, reopen the checkbox, preserve the previous acceptance record, and link the regression. If scope or profile coverage expands, keep the prior evidence and reopen the affected parent until the new requirements pass. Record only accepted changes to scope; do not move a required feature to later scope merely to close a milestone.
